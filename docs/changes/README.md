## 2. 完成功能后如何记录

1. 确认本次变更范围：有关提交、暂存和未暂存差异、新增源码、迁移及测试。围绕行为与规则归类，不按文件数量决定论文字数。
2. 在已有未完成批次追加本次相关条目，或为新的独立批次新建记录；新行为替代旧规则时引用旧编号，保留历史结论的适用版本，避免同时当作当前规则。
3. 对照需求、实际代码和证据写下差异，定位到文件及方法。已有测试但本次未运行，必须写“测试代码已存在；本次未执行”。接口字段、单位、访问范围、数据库关系和截图变化按实际影响记录。
4. 定向修正当前需求说明、技术底稿或接口说明中确定过时的段落；不重写无关章节，不覆盖历史验收报告。阶段完成后更新实施进度。
5. 在批次中维护文件覆盖清单并更新本页批次摘要。无论文影响的文件简记原因；共享文件可以关联多个编号。提交后补充提交号，不能据此抹去后续未提交差异。

纯拼写、内部命名或样式整理通常无需论文正文更新；若论文已有相关界面图，记录“仅检查／更新截图”。实现修复只有改变论文描述的行为、机制或实验结论时，才要求修改对应正文。

## 3. 更新论文时如何选范围

| 情况 | 核查和更新方式 |
| --- | --- |
| 小改动，来源和影响明确 | 读取相关条目、指定代码及必要调用链，检查受影响章节、图表和引用；仅修改相关内容 |
| 发现条目遗漏，但可明确界定影响 | 补记差异，扩大到相关流程或相邻章节核查，再做局部更新 |
| 主线／架构广泛变化、整体基线无法确定或遗漏影响不可界定 | 核查整个项目与论文的一致性，再决定哪些章节需要修改；不直接沿用缺漏文档 |
| 论文定稿 | 整体核对需求、代码、模型、接口、测试、图表、摘要和结论，完成版本登记 |

开始更新前，将论文已登记基线与当前提交比较，并检查工作区。以下为只读范围检查示例，`<论文基线>`替换为已核实的提交，不明时不得随意使用 `HEAD`：

```text
git log --oneline <论文基线>..HEAD
git diff --name-status <论文基线> HEAD
git diff --cached --name-status
git diff --name-status
git ls-files --others --exclude-standard
```

路径在旧清单中出现并不代表其后续修改已记录；继续检查相关 diff、方法和必要的调用关系。覆盖清单之外的代码变化先补记。历史文档日期不代表代码提交日期，也不证明当前环境已验收。

实际修改论文后，反查摘要、结论和图表是否引用了被修改的规则或结果。局部修改不需要强行更新这些部分，但相关引用不能保留矛盾。写作与排版遵循[论文规范](../thesis/论文写作与格式规范.md)。

## 4. 条目模板与状态

```markdown
### CHG-YYYYMMDD-NN 变更主题

- 来源与原因：需求来源；无法核实时注明“根据代码归纳”。
- 旧规则 → 新规则：行为、适用条件与必要边界；替代的旧条目编号。
- 代码依据：提交号，或基准提交＋审查时间＋未提交状态；文件路径、方法／类型、迁移。
- 实现状态：已存在实现／部分实现／待实现；代码与需求不一致的部分。
- 验证依据：报告、执行日期、适用代码版本和环境；测试文件与用例；未执行或缺少证据明确写出。
- 论文影响：章节主题、图表／截图、需核对的摘要或结论；只修改哪些内容。
- 论文状态：待核对／待更新／已同步／无需更新。
- 同步回填：论文文件和版本（提交号或 SHA-256）、修改日期、实际章节、已覆盖代码范围、剩余事项。
```

| 状态 | 含义 |
| --- | --- |
| 待核对 | 未检查目标论文对应内容，不能断言已写入或遗漏 |
| 待更新 | 已核实论文存在过时或缺失内容，尚未完成修改 |
| 已同步 | 已更新并复核目标论文，且已回填版本、章节和代码范围 |
| 无需更新 | 已核实该条目不影响目标论文，写明理由；纯内部调整也可据范围判断并说明 |

实现状态、验证状态、技术底稿状态和 Word 状态互不替代。批次含不同状态时显示“部分完成”及剩余编号；每次只改少数章节，不能将未处理条目一起标为已同步。

批次末尾附文件覆盖表，至少包含路径、已提交／未提交／新增来源、条目编号或无需更新原因。工作区快照可记录文件 SHA-256 用于后续识别同一路径的继续改动；不得归档密钥、原始照片、Cookie、签名 URL 或凭据。验证证据入口见[论文证据索引](../thesis/evidence-index.md)。
