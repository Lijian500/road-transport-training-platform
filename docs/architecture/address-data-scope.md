# 行政区域数据范围规则

## 目的与适用范围

本规则定义企业、行管组织与行政区域之间的关系，作为后续业务数据权限设计和查询实现的统一依据。本阶段只建立组织辖区模型，不实现跨组织业务数据查询。

`train_org.organization_nature` 表示根组织的业务性质：`ENTERPRISE` 为企业，`REGULATOR` 为行管；部门节点保持空值。`train_org.area_id` 关联 `sys_address.id`，以稳定主键保存组织辖区。当前架构中的 `enterprise_id` 仍表示租户根组织 ID，企业和行管均沿用该字段及既有租户隔离链路。

## 范围规则

- 平台管理员不受行政区域范围限制。
- 企业用户默认只能访问所属企业的数据。
- 行管组织的数据范围是其选中行政区域节点及全部下级区域内的企业：省级覆盖省内所有企业，市级覆盖市内所有企业，区县级仅覆盖本区县企业。
- 行管范围只包含企业组织，不自动包含同范围内的其他行管组织。
- 后续任何业务查询必须同时满足“功能权限 ∩ 行政区域数据范围”，不能只依赖前端筛选或隐藏数据。
- 行政区域缺失、节点不存在、层级异常或层级链断裂时，必须按无权限处理，不能扩大为上级或全量范围。
- 组织辖区修改后，后续新发起的查询立即按新范围生效；缓存实现不得延迟扩大旧范围。

## 范围解析约束

- 范围判断必须通过 `sys_address.parent_code` 的父子层级关系完成。
- 禁止使用地区名称、`merger_name` 或行政代码字符串前缀推断上下级关系。
- `area_id` 使用 `sys_address.id` 关联，不因行政代码编辑而改变组织绑定关系。由于 `sys_address` 使用 MyISAM，不建立数据库外键，写入时必须由服务校验地址存在且层级合法。
- 企业只能绑定三级区县节点；行管可以绑定一级省、二级市或三级区县节点。
- 解析行管范围时应一次解析目标节点及其下级节点集合，并批量参与业务查询，禁止对结果集逐行查询行政区域。

## 后续业务接入要求

- 后续业务表应保留所属根组织 ID，以便先识别数据所属企业，再应用辖区范围。
- 应提供统一的地址范围解析组件，由各业务服务复用，避免分别实现不同的层级判断规则。
- 服务端必须执行最终的数据范围校验；前端传入的组织 ID、地址 ID 或筛选条件只能作为查询条件，不能作为授权依据。
- 新增业务的设计、接口和测试应覆盖平台管理员、企业用户、行管省/市/区县范围、地址异常以及辖区变更等场景。
